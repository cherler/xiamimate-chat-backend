# 微信支付闭环实现、测试与操作说明

更新时间：2026-05-18

## 一、当前结论

本机 `xiamimate-chat-backend` 已完成微信 Native 支付第一版闭环的核心开发：下单、微信预下单、二维码展示、支付会话持久化、微信回调验签解密、复用内部到账编排、portal 轮询查单补偿。

当前已验证到“真实微信 Native 预下单成功并生成可扫码二维码”。真实用户扫码付款后的 paid 到账链路还需要一次小额人工支付验收；如果公网微信回调不能打到本机，portal 轮询会通过微信查单补偿把成功订单推进到账编排。

注意：本文不重复写入 API v3 Key、商户私钥、微信支付公钥等敏感内容。微信支付环境变量来源以 `docs/微信支付逻辑闭环操作清单-2026-05-16.md` 的 `4.2 环境变量` 为准。

## 二、实现说明

### 2.0 支付结果入口关系

`/internal/payments/provider-callback/wechat` 是内部到账编排入口，不是微信查单接口。它只接收已经被系统信任的“支付成功事实”，并负责把本地订单置为 `paid`、发放积分或订阅、应用促销和写账本。

微信支付成功事实目前有两个来源：

1. 微信服务器 notify：`POST /internal/payments/provider-notify/wechat`。
   - 先验签、校验时间戳、解密 `resource`、校验商户号/应用/金额/订单。
   - 校验通过且 `trade_state=SUCCESS` 后，调用内部 `provider-callback/wechat`。

2. 主动查单补偿：portal 轮询 `GET /portal/api/payments/orders/{order_id}` 或运维脚本主动查单。
   - 通过微信 `out_trade_no` 查单接口确认状态。
   - 查到 `SUCCESS` 后，调用内部 `provider-callback/wechat`。

同一笔成功支付只到账一次的保证来自多层：

1. `provider-callback/wechat` 对 `app.payment_order` 做原子状态流转，只有第一个事务能把非 paid 订单更新为 `paid` 并进入发放逻辑。
2. 后续重复 notify、重复查单、重复内部回调看到订单已 paid 时，只返回已处理结果，不再发放积分。
3. 内部回调带 `Idempotency-Key`，相同来源的重复请求会复用已完成响应。
4. `app.payment_order` 对 `provider_trade_no` 有唯一约束，防止同一微信交易号绑定多笔本地订单。

当前暂不支持微信原路退款，支付页面已提示“当前暂不支持线上原路退款，如需退款请联系人工处理”。

### 2.1 数据库

新增两张支付链路观测表：

1. `app.payment_session`
   - 保存微信 Native 支付会话。
   - 记录本地订单、用户、provider、channel、二维码 `code_url`、微信会话状态、过期时间、支付时间。
   - 一个 `app.payment_order` 可以对应多次支付会话，便于二维码过期后重新生成。

2. `app.payment_callback_event`
   - 保存微信 notify 原始事件、解密后 payload、验签结果和处理状态。
   - 用于排查签名失败、金额不一致、重复回调、内部到账失败等问题。

- `postgres/migrations/app/010_app_business_tables.sql`

### 2.3 微信支付服务层

新增 `data_platform/chat_backend/domains/payments/wechat_pay.py`，负责：

1. 校验微信支付配置完整性。
2. 加载商户私钥和微信支付公钥/平台证书。
3. 构造微信 API v3 `WECHATPAY2-SHA256-RSA2048` 请求签名。
4. 调用 Native 下单接口：`POST /v3/pay/transactions/native`。
5. 调用微信订单查询接口：`GET /v3/pay/transactions/out-trade-no/{order_id}`。
6. 校验 notify 请求头签名、时间戳窗口和公钥序列号。
7. 使用 API v3 Key 解密 notify `resource`。
8. 把微信交易状态转换成本地支付会话状态。

### 2.4 Portal API

新增/改造 portal 支付接口：

1. `POST /portal/api/payments/orders`
   - 创建本地 `app.payment_order`。
   - `provider=wechat` 时后续可创建微信 Native 会话。

2. `POST /portal/api/payments/orders/{order_id}/session`
   - 校验订单属于当前 portal 用户。
   - 校验订单仍为 `pending` 且 provider 为 `wechat`。
   - 调微信 Native 预下单。
   - 创建或复用 `app.payment_session`。

3. `GET /portal/api/payments/sessions/{session_id}/qr.svg`
   - 把微信返回的 `code_url` 渲染为 SVG 二维码。
   - 用户用微信扫一扫可直接支付。

4. `GET /portal/api/payments/orders/{order_id}`
   - 返回订单和最近支付会话。
   - 如果是微信 pending 订单，会调用微信查单接口做补偿刷新。
   - 查询到微信 `SUCCESS` 后，复用内部支付成功编排。

### 2.5 微信 notify API

新增：

```text
POST /internal/payments/provider-notify/wechat
```

该接口不使用内部服务密钥，安全边界来自微信支付 API v3 签名和 AES-GCM 解密。

处理顺序：

1. 读取原始 body 和微信支付请求头。
2. 验证必需请求头、时间戳窗口、公钥序列号和 RSA 签名。
3. 解密 `resource`。
4. 解析 `out_trade_no`、`transaction_id`、`trade_state`、`amount.total`。
5. 校验本地订单存在、provider 为 `wechat`、金额一致。
6. `trade_state=SUCCESS` 时调用内部 `provider-callback/wechat`。
7. 更新 `payment_session.status=paid`。
8. 落库 `payment_callback_event.processed_status=processed`。
9. 返回微信要求的成功响应：`{"code":"SUCCESS","message":"成功"}`。

### 2.6 Checkout 页面

`data_platform/api/chat_backend_portal_public_html.py` 已改造：

1. 支持选择微信支付。
2. 创建微信订单后自动调用 payment session API。
3. 展示微信 Native 支付二维码。
4. 每 2 到 3 秒轮询订单状态。
5. 支付成功后切换到成功态，并提供账户页入口。
6. mock 支付按钮仍保留，但只在 mock 开关开启时展示。


```bash
bash scripts/manage_wechat_pay_orders.sh cleanup --close-after-hours 24
```

```bash
bash scripts/manage_wechat_pay_orders.sh cleanup --close-after-hours 24 --apply
```

建议生产环境以 cron、systemd timer 或部署平台定时任务每 10 到 30 分钟执行一次 cleanup。cleanup 会先把已过期的 pending 二维码会话标记为 `expired`，再关闭超过阈值且没有有效待支付会话的 pending 订单。

3. 对微信 pending 订单，会调用微信 `out_trade_no` 查单接口做补偿。
4. 如果微信返回 `SUCCESS`，本机会调用内部 `provider-callback/wechat` 完成到账。

这意味着即使本机没有收到微信公网 notify，只要用户打开 checkout 页面等待轮询，也有机会通过查单补偿完成 paid 状态流转。

尚未实现的是独立的管理后台“按订单号主动查微信订单”按钮或 CLI 工具；目前查单能力内嵌在 portal 订单查询路径中。

### 5.2 退款逻辑是否实现

微信原路退款尚未实现。

当前已有的是内部积分退款能力：

```text
POST /internal/billing/refund-points
```

它用于报告/工具调用失败等场景，把已扣的积分退回到账本，属于平台内部积分退款，不是微信支付原路退款。

微信支付原路退款还需要补齐：

1. 退款业务表，例如 `app.payment_refund`。
2. 微信退款申请接口：`POST /v3/refund/domestic/refunds`。
3. 微信退款查询接口。
4. 微信退款 notify 验签、解密、落库。
5. 退款金额与订单金额、已退金额校验。
6. 订单和会话的 `refunded` / `partial_refunded` 状态流转。
7. 已到账积分或订阅权益的回收/冻结策略。
8. 管理后台或内部 API 的退款发起入口。

因此当前不要把“微信支付成功后可原路退款”作为已上线能力对外承诺。

## 六、除微信支付闭环外还需要做的工作

为了达到可上线标准，还建议补齐以下工作：

1. 持久化本机/生产微信支付环境变量，避免进程重启后配置丢失。
2. 用最低金额套餐完成一次真实扫码支付验收。
3. 验证 `3002 -> nginx -> portal` 主路径，不只看 `8200` 后端直连。
4. 确认公网 `https://xiamimate.com/internal/payments/provider-notify/wechat` 能正确转发到目标 chat-backend。
5. 增加正向 notify 测试样例，覆盖签名正确、解密成功、重复回调幂等。
6. 增加订单主动查单/运维查单工具。
7. 增加微信原路退款能力。
8. 增加二维码过期后的“重新生成”用户操作。
9. 增加订单关闭/超时清理任务，避免长期 pending 堆积。
10. 上线前确认 mock 支付只在本地或测试环境开启。

## 七、首版验收标准

首版微信 Native Pay 闭环可以按以下标准验收：

1. chat-backend `/health` 正常。
2. 微信支付配置完整，且日志不泄露密钥。
3. 从 `3002 -> nginx -> portal` 进入 checkout。
4. 选择微信支付并生成二维码。
5. 微信扫码付款成功。
6. portal 自动显示支付成功。
7. `app.payment_order.status=paid`。
8. `app.payment_session.status=paid`。
9. notify 可达时，`app.payment_callback_event.processed_status=processed`。
10. 积分包写入 `app.credit_ledger_entry`，月包写入/更新 `app.billing_subscription`。
11. 重复刷新、重复 notify 不重复到账。
12. 金额不一致或签名错误不会到账。
