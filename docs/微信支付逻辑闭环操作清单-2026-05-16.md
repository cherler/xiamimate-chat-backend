# 微信支付逻辑闭环操作清单

更新时间：2026-05-16

## 一、目标

把 portal 中的微信支付跑成一条可验证闭环：

1. 用户在 `/portal/products` 选择套餐
2. 进入 `/portal/checkout?package_code=...`
3. 创建本地业务订单 `app.payment_order`
4. 生成微信 Native Pay 二维码
5. 用户扫码支付
6. 微信支付回调到 chat-backend
7. 后端验签、解密、校验金额和订单归属
8. 复用现有内部支付回调编排，把订单置为 `paid`
9. 自动完成积分到账、订阅发放、促销兑现和 plan tier 更新
10. portal 轮询到支付成功，跳到账户页核对余额和账本

第一版只做微信 Native 二维码支付，不做微信 H5、JSAPI、小程序支付，也不做自动对账任务。

---

## 二、当前基础

当前 chat-backend 已经具备后半段能力：

1. `POST /portal/api/payments/orders`：portal 登录态下创建订单
2. `GET /portal/api/payments/orders/{order_id}`：portal 查询订单状态
3. `POST /portal/api/payments/orders/{order_id}/simulate-paid`：本地 mock 支付成功
4. `POST /internal/payments/provider-callback/{provider}`：内部支付成功编排入口
5. `app.payment_order`：本地业务订单表
6. 支付成功后的账本、订阅、促销、套餐层级联动已在 billing service 内实现

因此微信支付第一版不要重写账务逻辑，只补齐真实微信支付前半段：

1. 微信预下单
2. 支付会话持久化
3. 微信回调验签与解密
4. 原始回调事件落库
5. portal 二维码展示和等待态

## 三、我会怎么实现

### 3.1 数据库

在 `postgres/migrations/app/010_app_business_tables.sql` 中新增：

1. `app.payment_session`
   - 保存每次微信预下单会话
   - 一个 `payment_order` 可以对应多次支付尝试
   - 关键字段：`session_id`、`order_id`、`user_id`、`provider`、`channel`、`status`、`provider_order_id`、`provider_trade_no`、`cashier_url`、`qr_code_url`、`prepay_payload_json`、`expires_at`、`paid_at`、`created_at`、`updated_at`

2. `app.payment_callback_event`
   - 保存微信回调原始事件和处理结果
   - 关键字段：`event_id`、`provider`、`order_id`、`provider_order_id`、`provider_trade_no`、`event_type`、`signature_verified`、`payload_json`、`processed_status`、`processed_at`、`created_at`

在 `postgres/migrations/app/020_app_indexes.sql` 中新增必要索引：

1. `payment_session(order_id, created_at DESC)`
2. `payment_session(user_id, created_at DESC)`
3. `payment_session(provider, provider_order_id)`
4. `payment_callback_event(provider, order_id, created_at DESC)`
5. `payment_callback_event(provider, provider_trade_no, created_at DESC)`

修改 SQL 碎片后，执行：

```bash
bash postgres/scripts/rebuild_init_app_tables.sh
```

确保 `postgres/init_app_tables.sql` 作为兼容入口同步更新。

### 3.2 配置

在 `data_platform/chat_backend/infra/settings.py` 增加微信支付配置读取：

1. `CHAT_BACKEND_WECHAT_MCH_ID`
2. `CHAT_BACKEND_WECHAT_APP_ID`
3. `CHAT_BACKEND_WECHAT_API_V3_KEY`
4. `CHAT_BACKEND_WECHAT_PRIVATE_KEY`
5. `CHAT_BACKEND_WECHAT_PRIVATE_KEY_FILE`
6. `CHAT_BACKEND_WECHAT_CERT_SERIAL_NO`
7. `CHAT_BACKEND_WECHAT_NOTIFY_URL`
8. `CHAT_BACKEND_WECHAT_PAY_ENABLED`

私钥支持两种方式：

1. 环境变量直接提供 PEM 内容
2. 环境变量提供 PEM 文件路径

优先使用文件路径，便于生产环境挂载 secret，也避免 `.env` 中出现大段私钥。

### 3.3 微信支付服务层

新增支付域服务，例如：

1. `data_platform/chat_backend/domains/payments/wechat_pay.py`
2. `data_platform/chat_backend/domains/payments/sessions.py`

核心职责：

1. 构造微信 API v3 Authorization 签名
2. 调用微信 Native 下单接口
3. 保存 `code_url` 到 `app.payment_session`
4. 验证微信回调签名
5. 解密回调 `resource`
6. 校验订单号、金额、币种、交易状态
7. 写入 `app.payment_callback_event`
8. 转换成内部 `PaymentProviderCallbackRequest`

微信 Native 下单接口：

```text
POST https://api.mch.weixin.qq.com/v3/pay/transactions/native
```

请求里使用：

1. `out_trade_no = payment_order.order_id`
2. `amount.total = payment_order.amount_cents`
3. `notify_url = CHAT_BACKEND_WECHAT_NOTIFY_URL`
4. `description = 套餐名称或订单摘要`

### 3.4 Portal API

在 portal 路由中新增：

1. `POST /portal/api/payments/orders/{order_id}/session`
   - 入参：`provider=wechat`，可选 `channel=native`
   - 校验订单归属当前 portal 用户
   - 校验订单仍为 `pending`
   - 调微信 Native 预下单
   - 返回 `session`、`qr_code_url`、`expires_at`

2. `GET /portal/api/payments/orders/{order_id}/status`
   - 也可以先复用现有 `GET /portal/api/payments/orders/{order_id}`
   - 返回订单和最近支付会话状态

第一版优先复用现有查单接口，避免前端分叉太多。

### 3.5 微信回调入口

新增：

```text
POST /internal/payments/provider-notify/wechat
```

注意：这个接口是给微信服务器公网调用的，不使用 `X-Internal-Service-Secret`。安全边界来自微信支付 API v3 签名验证与回调资源解密。

处理顺序：

1. 读取微信请求头：`Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Signature`、`Wechatpay-Serial`
2. 读取原始 request body
3. 校验时间戳窗口，防重放
4. 用微信平台证书或微信支付公钥验签
5. 解密 `resource.ciphertext`
6. 落库 `payment_callback_event`
7. 找到 `payment_order`
8. 校验 `provider = wechat`
9. 校验 `amount.total = payment_order.amount_cents`
10. 校验 `trade_state = SUCCESS`
11. 更新 `payment_session` 状态
12. 调用或复用内部支付成功编排
13. 返回微信要求的成功响应

如果任何核心校验失败：

1. 记录事件为 `rejected` 或 `failed`
2. 不发放积分
3. 不开通订阅
4. 返回明确错误，便于日志排查

### 3.6 结算页改造

在 `data_platform/api/chat_backend_portal_public_html.py` 中改造 `/portal/checkout`：

1. 用户选择微信支付后，创建订单
2. 创建订单成功后自动调用 session 接口
3. 展示微信二维码
4. 展示过期时间和等待支付状态
5. 每 2 到 3 秒轮询订单状态
6. 订单变为 `paid` 后展示成功态
7. 提供跳转 `/portal/account#balance` 和 `/portal/account#topup`

本地 mock 支付按钮保留，但仅在 `CHAT_BACKEND_PORTAL_MOCK_PAYMENT_ENABLED=true` 时展示。

需要在本地或运行环境中准备以下配置。

1. 商户号 `mchid`: CHAT_BACKEND_WECHAT_MCH_ID
2. 应用 `appid`: CHAT_BACKEND_WECHAT_APP_ID
3. API v3 Key: CHAT_BACKEND_WECHAT_API_V3_KEY
4. 商户 API 证书私钥: CHAT_BACKEND_WECHAT_PRIVATE_KEY_FILE
5. 商户证书序列号: CHAT_BACKEND_WECHAT_CERT_SERIAL_NO
6. 微信支付平台证书或微信支付公钥: 微信支付公钥 
CHAT_BACKEND_WECHAT_PLATFORM_PUBLIC_KEY_ID 
CHAT_BACKEND_WECHAT_PLATFORM_PUBLIC_KEY_FILE
7. Native 支付权限
8. 回调公网 HTTPS 域名

### 4.2 环境变量

建议配置：

```bash
CHAT_BACKEND_WECHAT_PAY_ENABLED=true
CHAT_BACKEND_WECHAT_MCH_ID=...
CHAT_BACKEND_WECHAT_APP_ID=...
CHAT_BACKEND_WECHAT_API_V3_KEY=...

CHAT_BACKEND_WECHAT_CERT_SERIAL_NO=...
CHAT_BACKEND_WECHAT_NOTIFY_URL=https://your-domain/internal/payments/provider-notify/wechat
```

如果后续采用微信支付公钥模式，再补：

```bash

```

### 4.3 低金额测试套餐

建议准备一个专门用于真实支付验证的小额套餐，例如 1 分或 1 元。

## 七、成功性保障

### 7.1 订单归属

支付成功后的用户归属只允许来自：

```text
payment_order.order_id -> payment_order.user_id
```

不允许从前端 query string、回调 URL、回调 body 中直接读取 `user_id` 决定到账账户。

### 7.2 金额校验

微信回调中的 `amount.total` 必须等于：

```text
payment_order.amount_cents
```

不一致则拒绝处理，不置 paid，不发放积分，不开通订阅。

### 7.3 签名和解密

微信回调必须通过：

1. 请求头签名校验
2. 时间戳窗口校验
3. resource 解密
4. 商户号和 appid 校验

任何一步失败，都只落事件，不进入到账编排。

### 7.4 幂等

幂等约束来自多层：

1. `payment_order.status = paid` 后重复回调不重复发放
2. `provider_trade_no` 唯一约束防止同一微信交易号重复绑定
3. 内部 provider callback 使用 `Idempotency-Key`
4. 账本、订阅、promotion claim 保持既有幂等逻辑

### 7.5 等待体验

portal 等待态策略：

1. 二维码生成后立即展示
2. 每 2 到 3 秒轮询订单状态
3. pending 时显示“等待支付中”
4. paid 时显示成功，并提供账户页入口
5. expired 时提示二维码过期，并允许重新生成支付会话
6. failed 或 rejected 时展示明确错误，不误导用户重复付款

### 7.6 可观测性

每一笔支付至少能从四处排查：

1. `app.payment_order`
2. `app.payment_session`
3. `app.payment_callback_event`
4. `app.credit_ledger_entry` 或 `app.billing_subscription`

日志里需要能看到：

1. 微信预下单失败原因
2. 回调验签失败原因
3. 金额校验失败原因
4. 内部到账编排失败原因

敏感字段不能写入日志，例如 API v3 Key、商户私钥、完整证书内容。

## 九、回滚方案

如果真实微信支付出现问题，优先按以下顺序回滚：

1. 设置 `CHAT_BACKEND_WECHAT_PAY_ENABLED=false`
2. checkout 页面隐藏或禁用微信支付二维码生成
3. 保留订单查询和已支付订单到账逻辑
4. 保留 `payment_callback_event` 便于排查
5. 不删除历史订单、支付会话和回调事件

如果是部署级问题：

1. 回退代码版本
2. 重启 chat-backend
3. 确认 `/health` 正常
4. 确认 portal 订单查询仍可用

数据库新增表为向前兼容结构，正常不需要回滚 DDL。
