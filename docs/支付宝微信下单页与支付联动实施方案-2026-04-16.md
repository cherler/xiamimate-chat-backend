# 支付宝微信下单页与支付联动实施方案

更新时间：2026-04-16

## 一、这份方案解决什么问题

当前 portal 已经有：

1. 套餐与充值展示页
2. 订单创建能力
3. 支付成功后的账本发放、订阅发放、促销兑现能力

但还没有真正意义上的“下单页”与“支付收银台”体验。也就是说，用户现在能看到套餐，但还不能在 portal 中完成：

1. 选择支付方式
2. 调起支付宝或微信支付
3. 支付成功后自动回到账户页确认余额变化

本方案的目标，就是把这三个环节补齐，而且尽量复用现有 chat-backend 里已经实现好的订单与回调编排能力。

---

## 二、先说结论：当前基础其实已经有一半了

现有代码里已经具备比较关键的支付后半段能力：

1. [data_platform/chat_backend/api/public_routes.py](data_platform/chat_backend/api/public_routes.py) 已实现 `POST /v1/payments/orders`
2. [data_platform/chat_backend/api/internal_routes.py](data_platform/chat_backend/api/internal_routes.py) 已实现 `POST /internal/payments/provider-callback/{provider}`
3. [data_platform/chat_backend/domains/billing/service.py](data_platform/chat_backend/domains/billing/service.py) 已实现支付成功后的：
   - 充值积分到账
   - 月包订阅发放
   - promotion snapshot 兑现
   - plan tier 联动更新

这意味着：

1. “支付成功后如何和账户联动”这个核心账务问题，当前后端已经有主干实现
2. 现在缺的，不是从零开始做支付系统，而是补齐“支付前半段”和“用户支付体验层”

更准确地说，当前缺的是：

1. provider 级别的预下单能力
2. portal 下单页 / 收银页
3. 支付状态轮询与成功跳转
4. 支付宝、微信回调验签与事件落库

## 三、如果你是第一次接触支付，先理解 6 个概念

### 3.1 业务订单

业务订单就是我们自己的 `payment_order`。

它解决的是：

1. 这笔钱是谁付的
2. 付的是哪个套餐
3. 应该给这个用户加多少积分或开通什么订阅

当前系统已经有这层。

### 3.2 支付单 / 预下单

当我们去调用支付宝或微信时，还会生成一个“支付侧订单”或者“预支付会话”。

它解决的是：

1. 这笔业务订单在支付宝/微信那边对应哪个支付单
2. 应该展示二维码、收银台链接，还是 H5 唤起参数

当前系统还没有这层独立建模。

### 3.3 支付回调

用户付款完成后，支付宝/微信会通知我们的服务器。

回调的职责是：

1. 验证这条通知是真的
2. 确认金额没错
3. 确认 provider 和订单对应得上
4. 然后再把我们自己的 `payment_order` 置为 `paid`

当前系统已经有通用回调编排入口，但还没有支付宝/微信各自的官方验签接入。

### 3.4 状态轮询

支付页面上不能只靠“浏览器等着回调”，因为回调是 PSP 发给后端，不是发给前端页面。

所以 portal 下单页还需要定时轮询：

1. 当前订单还是 `pending`
2. 还是已经 `paid`
3. 如果已支付，就跳到成功页或者账户页

### 3.5 幂等

支付系统里，重复通知是常态，不是异常。

所以必须保证：

1. 同一个回调来 2 次、3 次，只发一次积分
2. 同一个订单不会重复开通订阅

当前系统内部回调已经有 idempotency 机制，这是非常好的基础。

### 3.6 对账

哪怕在线支付接通了，也不能完全相信单次回调。

后面还要补：

1. 每日对账
2. 异常订单巡检
3. 长时间 pending 的订单关闭

这部分不一定首期就做完，但架构上要预留。

## 四、推荐的产品形态：先做“统一下单页 + 双二维码支付”

### 4.1 为什么不建议第一版就做复杂 H5 / JSAPI

支付宝、微信都支持很多支付形态：

1. PC 收银台
2. H5 支付
3. Native 二维码支付
4. 微信 JSAPI
5. 小程序支付

对于当前 portal 来说，第一版最稳妥的方案不是一步上齐，而是：

1. Portal 里先做统一下单页
2. 支持两种支付方式：支付宝、微信
3. 桌面端优先用二维码支付

原因很实际：

1. 支付宝二维码和微信 Native Pay 都适合桌面 Web
2. 不依赖 OpenID、公众号、JSAPI 场景
3. 前端交互简单，两个支付方式的用户体验也更一致
4. 和当前 portal 的服务端渲染结构更匹配

### 4.2 推荐的用户路径

第一版建议这样设计：

1. 用户在 `/portal/products` 浏览套餐
2. 点击“立即下单”后，跳到受保护的 `/portal/checkout?package_code=...`
3. 下单页展示：
   - 套餐信息
   - 折扣信息
   - 最终应付金额
   - 支付方式切换：支付宝 / 微信
4. 用户选择支付方式后，后端生成对应的支付会话
5. 页面展示对应二维码
6. 页面轮询订单状态
7. 支付成功后跳到账户页或支付成功页
8. 用户在账户页看到余额、套餐或账本已经联动变化

## 五、与当前系统怎么衔接

### 5.1 当前已经有的主链路

现有链路可以概括为：

1. `POST /v1/payments/orders` 创建本地业务订单
2. 订单写入 `app.payment_order`
3. 支付成功后，调用 `/internal/payments/provider-callback/{provider}`
4. 回调内部把订单置为 `paid`
5. 然后自动执行：
   - 充值积分到账
   - 月包订阅发放
   - 促销奖励兑现
   - 套餐层级更新

这条链路里，真正要补的是 `第 2 步和第 3 步之间` 的 provider 侧支付接入。

### 5.2 所以不建议推翻现有订单模型

当前 `payment_order` 已经承载了：

1. `user_id`
2. `package_code`
3. `provider`
4. `amount_cents`
5. `promotion_snapshot_json`

因此第一版不要重写订单表，而是以 `payment_order` 为主订单，新增“支付会话层”。

## 六、建议新增的数据模型

### 6.1 `app.payment_session`

建议新增一张表，专门保存支付宝/微信的预下单结果。

建议字段：

1. `session_id`
2. `order_id`
3. `user_id`
4. `provider`
5. `channel`
6. `status`
7. `provider_order_id`
8. `provider_trade_no`
9. `cashier_url`
10. `qr_code_url`
11. `prepay_payload_json`
12. `expires_at`
13. `paid_at`
14. `created_at`
15. `updated_at`

用途：

1. 一个 `payment_order` 对应一次或多次支付尝试
2. 页面可以拿到二维码或收银台 URL
3. 支付过期、支付失败、重新拉起都有地方记录

### 6.2 `app.payment_callback_event`

建议新增一张原始回调事件表。

建议字段：

1. `event_id`
2. `provider`
3. `order_id`
4. `provider_order_id`
5. `provider_trade_no`
6. `event_type`
7. `signature_verified`
8. `payload_json`
9. `processed_status`
10. `processed_at`
11. `created_at`

用途：

1. 保留原始通知
2. 便于排查支付异常
3. 为后续对账任务提供基础数据

## 七、推荐的 API 设计

### 7.1 Portal 侧接口

建议新增：

1. `POST /portal/api/payments/orders`
   - 作用：在 portal 登录态下创建订单
   - 也可以复用现有 `/v1/payments/orders`，但 portal 独立接口更利于前端语义清晰

2. `POST /portal/api/payments/orders/{order_id}/session`
   - 作用：为指定订单生成支付会话
   - 请求参数：`provider=alipay|wechat`
   - 返回：二维码 URL / 收银台 URL / 过期时间

3. `GET /portal/api/payments/orders/{order_id}/status`
   - 作用：前端轮询支付状态
   - 返回：`pending|paid|expired|closed|failed`

4. `POST /portal/api/payments/orders/{order_id}/close`
   - 作用：关闭未支付订单
   - 非首期必需，但建议预留

### 7.2 Provider 回调接口

建议拆成 provider 专属入口，而不是直接把官方通知打到通用路由。

建议新增：

1. `POST /internal/payments/provider-notify/alipay`
2. `POST /internal/payments/provider-notify/wechat`

职责：

1. 验签
2. 解析官方回调字段
3. 转换成系统内部标准结构
4. 再调用现有通用编排逻辑，或者直接复用其中的核心函数

这样做的好处是：

1. 官方协议与内部业务逻辑解耦
2. 支付宝、微信差异不会污染通用支付服务

## 八、支付宝与微信各自建议怎么接

### 8.1 支付宝

第一版建议优先接：

1. 桌面端二维码支付方案
2. 第二阶段再补 H5 WAP 收银台

服务端大致需要：

1. `app_id`
2. 商户私钥
3. 支付宝公钥
4. `notify_url`
5. 商户订单号，建议直接使用 `order_id`

服务端职责：

1. 调支付宝预下单接口
2. 保存返回的二维码或收银参数到 `payment_session`
3. 收到支付宝回调后验签
4. 验证金额、订单状态、provider 一致性
5. 再驱动现有订单支付成功编排

### 8.2 微信支付

第一版建议优先接：

1. Native Pay 二维码支付
2. 后续阶段再补 H5 / JSAPI

服务端大致需要：

1. `mchid`
2. `appid`
3. API v3 Key
4. 商户证书私钥
5. 证书序列号
6. `notify_url`

服务端职责：

1. 调微信 Native 下单接口
2. 保存 `code_url` 到 `payment_session`
3. 回调时校验签名并解密资源
4. 验证金额、订单号、支付状态
5. 再走内部统一支付成功编排

## 九、支付成功后如何和账号联动

这是最关键的一点，也是当前系统已经具备明显优势的地方。

### 9.1 正确的联动原则

支付成功后的发放逻辑，必须只认我们自己的订单，不认前端传来的用户信息。

正确链路应该是：

1. 用户登录后创建 `payment_order`
2. `payment_order` 已经绑定 `user_id`
3. PSP 回调只告知“某个 order_id / out_trade_no 已支付”
4. 后端根据该订单拿到 `user_id`
5. 然后给对应账户发放积分或订阅

### 9.2 当前系统已经具备的联动能力

现有回调逻辑已经做到：

1. 充值包支付成功：给对应 `user_id` 加积分账本
2. 月包支付成功：开通或续期订阅
3. 促销奖励：按 promotion snapshot 发放
4. 套餐升级：按 package meta 更新用户 plan tier

也就是说，真正要保证的是：

1. PSP 回调一定能可靠映射到正确的 `payment_order`
2. 回调验签和金额校验必须足够严格

### 9.3 第一版不要做的危险事情

不要在支付成功回调里：

1. 依赖前端传回 user_id
2. 依赖 query string 决定给谁发积分
3. 绕开 `payment_order` 直接改账本

必须始终以 `payment_order.order_id -> user_id` 为唯一归属关系。

## 十、下单页建议长什么样

建议新增一条受保护路由：

1. `/portal/checkout`

页面结构建议：

1. 左侧：订单摘要
   - 套餐名称
   - 基础价格
   - 折扣
   - 最终应付
   - 预计到账积分

2. 右侧：支付方式
   - 支付宝
   - 微信支付

3. 下方：支付状态区
   - 待支付
   - 支付中
   - 支付成功
   - 已过期 / 已关闭

4. 操作按钮
   - 创建订单
   - 生成二维码
   - 刷新状态
   - 支付成功后回到账户页

### 10.1 建议的前端交互顺序

1. 用户选择套餐
2. 创建订单
3. 页面拿到 `order_id`
4. 用户选择支付宝或微信
5. 调用 session 接口生成二维码
6. 每 2 到 3 秒轮询一次订单状态
7. 如果订单变成 `paid`，展示成功态并跳转 `/portal/account#balance`

## 十一、推荐实施阶段

### Phase 1：先把支付骨架补齐

范围：

1. 新增 `payment_session`
2. 新增 provider notify 路由
3. Portal 下单页 HTML
4. Portal 订单状态轮询
5. 先支持“模拟支付成功”联调

目标：

1. 让 portal 完整跑通从下单到账户到账的产品链路

范围：

1. 支付宝预下单
2. 支付宝回调验签

目标：

1. 先让一种真实支付方式在线可用

范围：

1. 微信 Native 预下单
2. 微信回调验签与解密

目标：

1. 形成双支付方式闭环

### Phase 4：补移动端体验与对账

范围：

1. 支付宝 WAP / 微信 H5 或 JSAPI
2. 支付成功页优化
3. 关闭超时订单

## 十三、风险与注意事项

### 13.1 金额必须严格匹配

回调里必须校验：

1. PSP 实付金额
2. `payment_order.amount_cents`

如果不一致，不能发积分，也不能开订阅。

### 13.2 回调永远不能直接改用户归属

只允许：

1. `order_id -> payment_order -> user_id`

不允许任何外部字段直接决定到账账户。

### 13.3 回调、轮询、刷新会重复发生

必须保证：

1. 订单幂等
2. 账本幂等
3. 订阅发放幂等
4. promotion claim 幂等

### 13.4 长时间 pending 订单需要关闭

否则后面会出现：

1. portal 里订单过多
2. 用户重复扫码旧订单
3. 支付状态混乱

---

## 十四、最小可行实施建议

如果按“最小可行”来做，我建议不要同时硬上支付宝 H5、微信 H5、微信 JSAPI。

最务实的顺序是：

1. 先做 portal 下单页
2. 先做统一订单状态轮询
3. 先做支付宝二维码支付
4. 再做微信二维码支付
5. 最后再补移动端特化支付

这样能最快拿到一条真正可用的“浏览套餐 -> 下单 -> 扫码支付 -> 账户到账”的完整链路。

---

## 十五、下一步建议

如果继续推进实现，建议马上进入以下顺序：

1. 先补数据库与 provider 抽象层
2. 再补 `/portal/checkout` 和 portal 支付接口
3. 先做 mock provider 联调
4. mock 跑通后，先接支付宝，再接微信

这是当前代码基础上最稳、也最省返工的一条路。
